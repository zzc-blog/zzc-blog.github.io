1. 原码、反码、补码

  1. 正数的原码、反码、补码都一样
  2. 负数的原码，就是最高位使用符号 1，代表负数，如 8bit 表示：10000010 代表 -2 的原码，反码就是符号为不变，其他位按位取反（0-> 1,1-> 0），得到 11111101,

补码=反码 + 1，得到补码：11111110

8 位来算：2 的补码 + -2 的补码 = 0000 0010 + 1111 1110 = 1 0000 0000，溢出，相当于 0

  1. 计算机中的计算都是使用补码来算的，底层存储的 bit 都是一样的，只是解读方式不一样

A - B = A + (-B), A-B 相当于 加上 -B 的补码，-B = ~B + 1

3. long 转字节数组 相互转换

为什么要进行转换？

答：long 在 Java 是 64 位，8 个字节。网络传输，要把一个 64 位 long 数字，拆成 8 个 byte 字节数组，才能放到网络报文里发送。

为什么网络只能一个字节一个字节往外发，不能直接发 64 位 long？

1、硬件底层：网卡、TCP/IP 协议，设计的传输单位就是字节（8bit）

网卡在物理链路上，是以比特 bit 一位一位传的，但是协议层把 8 个 bit 打包成 1 个字节 byte，作为最小处理单元。

2、TCP 是字节流协议

TCP 是面向字节流：它传输的是一串无差别的字节序列。 TCP 只关心：“我要发送 N 个字节的数据”，它完全不懂上层的 Java 数据类型：long、int、double。

3、还有一个致命问题：大小端（字节序）

就算假设网卡可以直接丢 64 位整数：

  • 有的 CPU 是小端：内存里低字节放前面；
  • 有的 CPU 是大端：内存里高字节放前面。

同一 long 数字，在不同 CPU 内存里，字节摆放顺序是反过来的。 如果直接把内存里的 long 二进制原样丢上网络，小端机器发的数据，大端机器收到解析出来就是完全错误的数字。

所以网络协议强制约定：统一使用大端序（网络字节序）。 我们的longToBytes，就是手动按大端顺序，把 long 拆成字节数组。

4、内存存储 vs 网络传输，两件不一样的事

  1. CPU 内存里的 long：64 位，8 字节，CPU 可以直接读写，受本机 CPU 字节序影响。
  2. 网络上传输：跨机器通信，必须定义一个与 CPU 无关的标准二进制格式，也就是大端字节数组。

直接把内存的 long 扔网络：不同机器解析结果不一样，协议就乱套。 所以必须我们手动做转换：long → 大端 byte []。
