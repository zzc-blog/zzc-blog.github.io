3. proot 容器服务自启动原理

很多人以为「把服务脚本放进 /etc/profile.d 就能开机自启」，这句话只说对了一半。

3.1 /etc/profile.d 到底何时执行

关键结论：/etc/profile 会加载 /etc/profile.d/*.sh，而 /etc/profile 仅在登录 shell（bash -l）才执行。

场景 是否执行 /etc/profile.d
proot-distro run ubuntu bash -l（登录 shell） ✅ 执行
proot-distro run ubuntu bash（普通 shell） ❌ 不执行
后台服务、systemd ❌ 不读取

所以把服务脚本丢进 /etc/profile.d/，只能实现「手动进入交互式登录容器时启动」，不能实现后台开机自启。

3.2 交互式登录自动启动的用法

3.3 三个必须避开的坑

  1. proot-distro login ubuntu 默认不是登录 shell（不带 -l），脚本不会跑；
  2. 多次进入容器会重复执行脚本，需加进程检测：
  3. 这不是真正的开机自启——Termux 重启、容器没运行时不会自动跑；proot Ubuntu 无 systemd。

3.4 三种真正可落地的方案

方案 触发时机 缺点 使用条件
A. /etc/profile.d 手动登录进入交互式 shell 不登录不启动；重复执行；不能常驻 必须 -- bash -l
B. proot-distro 启动钩子 容器启动就运行 — 修改 /data/data/com.termux/files/usr/etc/proot-distro/ubuntu.sh
C. Termux 侧自启动 Termux 开机先启容器 proot 会话结束进程销毁 需 tmux 套一层常驻

13.7 故障排查经验集

① 僵尸在线：pgrep -x minio 有 PID 但端口全拒、日志 0 字节。排查 ps aux | grep minio 看 STAT 是否 S/D、数 socket fd、curl 实测端口。根因是进程异常沉睡未完成端口绑定，start-minio.sh restart 解决。教训：进程存在 ≠ 服务正常，必须用 curl 做健康检查。

② frpc 隧道不通：依次查进程 → 日志 → 后端端口 curl → pid 文件是否残留。常见根因：后端没起来、pid 残留导致脚本跳过启动、域名配置不对。

③ 端口探测手法：curl -s -o /dev/null --max-time 2 -w "%{http_code}" http://127.0.0.1:PORT + pgrep -x 服务名。

④ no_proxy 通配坑：不支持 *.domain，裸域名已匹配子域名，不要加星号。

⑤ 端口冲突：mihomo external-controller 从 9090 改 9097 避开 SearXNG，新增服务先查端口表。

⑥ MinIO 预签名 URL 指向内网：必须设 MINIO_SERVER_URL 为公网域名。

结语

一台手机从「能跑 Linux」到「承载十几个服务的家庭服务器」，关键不在某个单独的工具，而在一套连贯的方法：用 Termux + proot 搭出环境，用 Nginx 做统一网关，用脚本体系替代 systemd 做服务管理，用 frp/cloudflared/Tailscale 解决公网访问，最后用「进程活着 ≠ 服务正常」这类经验守住稳定性。本文覆盖的每一条命令和配置都来自实际运行环境，可直接对应真实文件，供按需取用和二次修改。

本文基于 Termux + proot-distro Ubuntu 环境整理，源文件中的明文密码、token、secret、隧道 UUID 等凭据已脱敏为占位符。
